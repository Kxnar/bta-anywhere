# Proposed design: encrypted guest companion (Workstream 3)

**Status:** Design accepted by the maintainer on 25 September 2026 for implementation after Workstreams 0 and 1 pass; no feature code exists and release is not approved
**Original design base:** `main` at `05d0c2d4c54a0525316aa2bdd2621d73f0c20456`
**Current review base:** `origin/main` at `fdc7ef45fdf99637a5f710d7d8931b63ca4e7485`; the accepted design is carried forward without feature implementation
**Target:** Windows x86-64, Java 17 bytecode/JDK 21 runtime, self-hosted relay
**Decision owner:** Project maintainer

This proposes an optional way for a stock BTA guest client to join through a local companion while the relay cannot read or alter game payloads undetected. It adds no account service or public relay. LAN, Direct, and the existing unencrypted Relay mode remain separately selectable. The invitation is transferred over a trusted, authenticated channel outside BTA's control. A person who obtains it can race the intended guest to redeem it.

## Decision and trust boundaries

```text
Stock BTA guest -> 127.0.0.1 guest companion
  -> TLS 1.3 to self-hosted relay (relay identity checked)
    -> opaque stream over existing host QUIC connection
      -> TLS 1.3 to host tunnel (host identity checked)
        -> authenticated, bounded game-byte framing -> 127.0.0.1 managed BTA server
```

The **inner TLS connection** begins at the guest companion and ends at the host tunnel, after the relay's `ConnectionOpen` header. Only the host tunnel opens the local server connection, and only after inner TLS, host identity, and the invitation capability have passed. The relay terminates outer TLS and host QUIC, but only forwards inner TLS records. This is TLS 1.3 as specified by [RFC 9846](https://www.rfc-editor.org/info/rfc9846/), a standards-reviewed protocol that supersedes RFC 8446; this design does not claim an external audit of BTA code. No custom cipher, MAC, KDF, signature, or random-number algorithm is proposed.

The guest's trust anchor is the invitation received through the authenticated outside channel. It contains a session-specific **host certificate SPKI SHA-256 pin** and relay DNS name, TCP endpoint, and **relay certificate SPKI SHA-256 pin**. For a fresh guest, the authenticated invitation's relay pin is the trust anchor for the outer relay TLS connection; the guest does not need a separately distributed relay CA file. The guest validates the presented certificates' signatures and validity, the relay certificate's DNS subject alternative name, the exact host and relay SPKI pins, TLS 1.3, and the expected ALPN values. A private or self-signed relay certificate is accepted only when these checks pass under the invitation pin. The guest never accepts a certificate or protocol override interactively after a mismatch. The host's trust anchor for guest admission is a 256-bit, one-use invitation capability it generated; BTA online mode and the whitelist remain authoritative for player identity and access. The relay access token still only allocates relay capacity and is never put in an invitation.

The host's certificate key is generated for one hosting session and kept in memory; its pin is a **session identity, not a permanent human identity**. An authenticated invitation channel is necessary to bind that pin to the intended host. On host-process restart, all invitations and the ephemeral key are revoked; after safe process recovery, the host must establish a new encrypted session and issue new invitations. A tunnel reconnect in the same host process retains the key, but a game TCP connection interrupted by a tunnel failure is not transparently resumed.

## Wire and mode separation

Add a versioned host-to-relay registration (`bta-anywhere/2`) with an explicit `encrypted-guest` session mode and a distinct host QUIC ALPN `bta-anywhere/2`. The encrypted host offers and requires only that ALPN on initial connection and every reconnect; the relay may separately offer `bta-anywhere/1` to legacy hosts, but a v2 session never negotiates or falls back to v1. A v2 `ConnectionOpen` header must match the host's locally selected encrypted mode and session before any inner TLS processing. Its allocated guest TCP listener requires outer TLS 1.3 with ALPN `bta-anywhere-relay/1`; the Rust relay can use its existing `rustls` dependency plus a maintained Tokio adapter. The relay certificate is the same identity presented to the host on QUIC, so the host can bind the pin into the invitation. The Java guest verifies its relay DNS reference identity and the invitation's exact relay pin. The relay then forwards bytes without parsing the inner TLS or application frames. Existing v1 registration and raw guest listener remain unchanged and labelled **Legacy relay: relay can read game traffic**. No v1 fallback from an encrypted invitation, even when v2 is unavailable. An old relay produces a clear unsupported-version error.

The guest companion opens two nested TLS 1.3 connections: outer to the relay and inner to the host, with inner ALPN `bta-anywhere-guest/1`. The host tunnel uses a Java `SSLEngine`/Netty `SslHandler` on its guest QUIC stream, before its local-TCP bridge. The guest may use layered JSSE `SSLSocket`s or equivalent Netty handlers; the implementation must prove nested handshakes, backpressure, and shutdown on Windows before choosing between them. The inner host certificate is a self-signed, session-specific X.509 certificate made with Java `KeyPairGenerator`/`SecureRandom` and a maintained X.509 builder such as Bouncy Castle PKIX; Java JSSE performs TLS and signature validation. The guest accepts that certificate only under the invitation's exact SPKI pin, validates its signature, allowed algorithm and validity, and rejects a wrong pin. Java TLS and ALPN configuration are documented by [Oracle's Java 17 JSSE guide](https://docs.oracle.com/en/java/javase/17/security/java-secure-socket-extension-jsse-reference-guide.html) and [SSLParameters API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/net/ssl/SSLParameters.html). Certificate identity checks must follow the appropriate [RFC 9525](https://www.rfc-editor.org/info/rfc9525/) rules for the relay DNS name; the host's out-of-band pin is a separate trust mechanism.

Within inner TLS, use a small versioned binary envelope for `AUTH`, `AUTH_OK`, `DATA`, `FIN`, and `ERROR`: one-byte type plus unsigned 16-bit length, with a maximum 16 KiB payload. `AUTH` contains the invitation ID, **status or join intent**, corresponding capability, host-session ID, and application version, with a maximum 2 KiB body. `DATA` contains game bytes; `FIN` means TCP write-half-close while the opposite direction continues. Unknown types, excess lengths, frames before authentication, truncation, and missing clean TLS closure fail closed. This is application framing, not a new cryptographic protocol. The relay sees only outer TLS plaintext containing **inner TLS ciphertext**; its per-direction forward buffers remain bounded (proposed 64 KiB each), with existing stream/session quotas, read backpressure, handshake deadlines, idle timeouts, and no content-dependent logs. The host must enforce its own limits even if a hostile relay bypasses relay quotas: at most eight encrypted guest streams per session including unauthenticated inner handshakes, at most 64 KiB buffered before `AUTH` per stream, a ten-second deadline from stream open through `AUTH`, and at most 64 outstanding invitations per hosting session. Reaching a cap rejects new work without evicting an active invitation or opening a local server socket. These are proposed upper bounds to verify against Workstream 0 before implementation, not benchmark targets; limits must never be raised solely to pass a benchmark.

## Invitation and join flow

1. After the managed server is ready and the encrypted relay session is allocated, the host selects **Create encrypted invitation**. It generates independent random 256-bit **one-use join** and **status-only** capabilities and a random invitation ID, stores only constant-time-comparable digests plus session binding and issue/deadline state within the outstanding-invitation cap, and displays a copyable `BTAE1` invitation. The invite contains format/protocol version, host-session ID, host SPKI pin, relay DNS/TCP endpoint, relay SPKI pin, absolute expiry for display, both scoped capabilities, and their intents. It contains no world path, relay allocation token, long-lived key, or username. Format is canonical, strictly parsed, and size-capped at 2 KiB. It is never a command-line argument, browser URL, metric label, exception, or normal log field.
2. The host sends the invitation over a trusted authenticated channel outside BTA. The guest imports it into the companion on Windows. The companion displays the host-session fingerprint, relay endpoint, and expiry, and binds an ephemeral listener to `127.0.0.1` only. It tells the player to join that local address from the ordinary BTA client. On each local TCP connection it buffers the first byte, with a short timeout, to distinguish a BTA 8.0.1 server-list status probe (`0xFE`) from a join handshake (`0x02`). For a probe, it parses the remaining request with a strict size and time bound to determine the supported status/icon variant. Unknown, partial, malformed, or oversized input closes without contacting the relay or spending either capability.
3. For a valid `0xFE` probe, the companion checks format/version, relay identity, and host pin, establishes both TLS layers, and sends status `AUTH` **inside inner TLS** with the status-only capability and the validated status/icon variant. The host verifies its scope and deadline without consuming the join capability. The host constructs a fixed, bounded BTA status request for that variant to its local server, returns only the bounded status/icon response through inner TLS, then closes the status connection. Guest-supplied bytes are never forwarded to the server on this path, and no status connection can upgrade to game traffic. The companion sends the response to the local BTA ping socket. Repeated status probes may use the status capability until the invitation expires or is revoked, subject to a per-invitation rate limit and the existing connection quotas.
4. For a `0x02` join handshake, the companion checks format/version, relay identity, and host pin, establishes both TLS layers, sends join `AUTH` **inside inner TLS**, and waits for `AUTH_OK`. The host atomically checks and consumes the join capability before opening a local BTA server socket. A failed or concurrent duplicate receives a generic denial, with no game traffic forwarded. The companion then forwards its buffered first byte and bridges framed game bytes and directional `FIN`, preserving EOF semantics. A failed login after redemption still requires a new invitation.
5. A successful join redemption consumes the **join capability**; a status probe never does. Every later game connection, including after a guest, relay, or host tunnel disconnect, requires a **new invitation**; there is no implicit resume capability in v1 of this feature. If the relay endpoint changes on registration, outstanding invitations are invalidated and reissued. Host stop, explicit revoke, expiry, host key rotation, or process restart also invalidates both capabilities. This limitation should be prominent in setup/troubleshooting text.

**Why the split is necessary:** read-only inspection of the cached, pinned BTA 8.0.1 client JAR (`minecraft-client-deobf-8.0.1.jar`, SHA-256 `ef37a8bc0f9c51b73336bdf9b23e6961f53c6afef967409d661795642187672b`) shows `ThreadPingServer` opening a separate TCP socket and sending `PacketPingHandshake`, mapped to packet ID `0xFE`; `ScreenConnecting` instead sends `PacketHandshake`, mapped to `0x02`. The game can therefore ping the companion before the player clicks Join. This bytecode check is evidence for the proposed classifier, not a substitute for a real BTA 8.0.1 server-list and join test. The status response shape, optional icon, and probe timing still need validation on a disposable server; an incompatible probe must block the utility gate rather than consume the join token or fall back to plaintext.

The host's monotonic clock decides expiry while its process is alive (proposed ten minutes maximum), so rolling its wall clock back cannot extend an invitation. The absolute expiry in the invitation is for the guest's display and early rejection; if the guest clock is wrong, the host still decides admission. A badly wrong guest clock can also make TLS certificate validation fail, which must produce an actionable clock error without a verification bypass. Restart revokes all outstanding invitations, so no wall-clock reconstruction is needed. A host clock too far wrong when generating its certificate blocks joins until corrected.

## Threat and failure model

| Event | Required result |
| --- | --- |
| Relay reads or modifies traffic | It sees outer TLS plaintext containing inner TLS records, source/destination addresses, session/port, timing, traffic volume, TLS handshakes and record sizes. It cannot recover game bytes or forge accepted inner TLS application data without host key material. Modification, reordering, truncation, and replay fail inner TLS or application checks, or cause a visible disconnect. Availability remains under relay control. |
| Stolen invitation | First successful **join** redeemer wins; the attacker may join until BTA authentication/whitelist rejects them. The status capability only permits bounded server-list queries until expiry. Host can revoke both before use. The invitation must therefore use a trusted channel and short lifetime. No claim of non-transferability. |
| Replayed handshake or capability | TLS 0-RTT and TLS ticket resumption are disabled for both guest links; each connection uses a full TLS handshake. Post-handshake join-capability redemption is atomic and one-use; a replayed join `AUTH` is denied. Status replay can only repeat rate-limited, read-only probes while valid. A replayed TLS transcript cannot authenticate as a new session. |
| Status probe then join | The `0xFE` socket uses status-only authorization and closes after a constructed status query. It never consumes the join capability, forwards arbitrary guest bytes, or upgrades to a game socket. A separate `0x02` connection uses join authorization. |
| Wrong host, relay, key, ALPN, or version | Pin/identity/version mismatch closes the local join with a clear error; never retry as legacy/plaintext. |
| Expired/revoked invitation, wrong clocks | Host rejects by monotonic deadline or revocation. Guest may reject early; clock diagnostics guide correction without overriding checks. |
| Relay, host tunnel, or companion exits | Close both halves, release active-stream gauges and buffers, keep world recovery logic unchanged. BTA may reconnect only through a new invitation. Do not kill a process by PID alone or restore a backup automatically. |
| Plain BTA client points at encrypted public port | Outer TLS handshake rejects it before forwarding to host. The relay may see those accidental bytes; documentation directs guests to the companion's loopback endpoint only. |

TLS protects confidentiality and integrity of **game payloads between companion and host tunnel**, subject to correct implementation and uncompromised endpoint keys. It does not hide the host/guest IPs, relay port, timing, volume, traffic shape, availability, or information that the BTA server itself, guest client, gameplay mods, or host operating system reveal. The host and guest must continue to trust their own machines. Do not claim a security audit of this implementation.

## Invariants, changes, and validation plan

Affected invariants: world ownership, explicit backup restoration, process identity checks, TLS verification, redaction, bounded framing/queues, quota enforcement, and clean half-close. Encryption is added after the existing save/unload and server-readiness gates, with no change to the managed world's lifecycle. The host's locally selected encrypted mode is authoritative: a relay-supplied header cannot switch a stream to the legacy bridge. No local server socket is opened before inner TLS and a valid, scoped invitation `AUTH` complete.

Likely code boundaries after approval: `relay/src/{main,state,config,protocol}.rs` for v2 registration/outer TLS/opaque forwarding; `tunnel-client` for host-side inner TLS and invitation admission; a separate guest companion entry point in `tunnel-client` for loopback join; `bta-mod` hosting UI for invite/revoke; shared test vectors under `protocol/test-vectors/`; `docs/{protocol,architecture,security,privacy,building,quick-start,troubleshooting,releasing}.md`. Final file placement and dependencies require implementation review. Never write invitations, private keys, saves, generated certs, or raw private logs to Git.

Tests must include fresh-account Windows install/join on a disposable world, including a private-CA or self-signed relay using only the invitation as the guest's trust anchor; **server-list probe before Join with and without an icon, repeated probe without join-token consumption, malformed/slow/unknown first byte, status-to-game upgrade attempt, status flood and expiry**; expired and revoked invites, two concurrent join redemptions, invitation copied to wrong host/relay, host/relay key rotation, modified/replayed/truncated inner TLS, malformed outer and inner TLS, unsupported ALPN/version on initial connection and reconnect, a malicious relay sending a v1 header or raw bytes into a v2 host stream, plaintext-to-encrypted port, wrong guest/host clock, host/relay/companion crash, port reallocation, byte equality, half-close, host-side handshake/invitation caps, bounded-memory/handshake flood, log/metric redaction, and no local server socket before valid inner `AUTH`. Deterministic public-only vectors cover invitation parsing and authenticated application frames; no live secrets enter the corpus. Run the existing serial and concurrent Windows harnesses **sequentially**.

Workstream 0 must first supply a stable same-machine release-build baseline. Workstream 1 must pass its existing-protocol conformance and adversarial-framing gates before Workstream 3 implementation begins. Workstream 3 owns the new v2 cross-language vectors, conformance cases, and adversarial tests; they must pass before Workstream 3 is review-ready. Then compare encrypted and legacy sessions in alternating order on identical 1/8-stream, 1 KiB/64 KiB/1 MiB, bidirectional, half-close, reconnect, CPU/memory, and invitation-handshake cases. Keep the specified gates: at eight streams no more than 15% median throughput reduction, 5 ms added loopback p95 latency, 500 ms p95 invitation handshake, or 30 MiB extra steady-state memory per endpoint; a two-hour eight-stream encrypted soak and five clean Windows integration passes are required. A miss blocks merge and retains measurements. A fresh guest tester records setup time and confusion points. Baseline, commands, hardware/OS/JDK/Rust, commit, configuration, run counts, payloads, and raw JSON locations must accompany review. **No baseline or candidate measurements exist in this design branch.**

Rollback after a failed experiment: close/revoke encrypted sessions and companion; disable encrypted mode; keep LAN, Direct, and explicit legacy Relay available; leave the managed server and world journal to their existing stop/recovery procedure. No manual world edits or automatic backup restoration. Removing the branch or reverting the feature must not require converting world data.

## Accepted design decisions and dependency check

As of 26 September 2026, the benchmark and protocol code from Workstreams 0
and 1 has reached `origin/main`, but their documented acceptance gates are not
closed. `docs/benchmark-review.md` records an intermittent eight-stream
relayed throughput stall, an incomplete stable full baseline, and no completed
two-hour soak. `docs/protocol-stacked-review.md` records a corrected 10,000-case
cross-language run but still requires the final four-target long campaign,
repeated integration, comparison, and soak evidence. A merged code path alone
does not satisfy this design's implementation precondition. The first planned
implementation increment after those gates is a Windows disposable-server
prototype for nested TLS and the real BTA server-list status/join split; its
results must resolve the open JSSE/Netty composition and status-response
questions before relay or UI integration.

- The maintainer accepted invitations exchanged over a trusted authenticated outside channel, without a BTA account service or additional guest identity binding in this first iteration.
- The maintainer accepted session-specific host identity and a **new invitation for every join or reconnection**. A persistent host identity or resumable invitation would require a separate lifecycle and storage design.
- The maintainer accepted outer guest TLS on encrypted ports of the self-hosted relay. This does not authorize a public service or higher default quotas.
- The certificate-generation dependency and exact JSSE/Netty composition still require a Windows prototype before implementation. As of 25 September 2026, the current repository pins `rustls 0.23.43` and Netty `4.1.122.Final`; official documentation shows active [rustls 0.23 maintenance](https://github.com/rustls/rustls/security), [Tokio Rustls](https://docs.rs/tokio-rustls/latest/tokio_rustls/server/struct.TlsAcceptor.html), [Netty 4.1 `SslHandler`](https://netty.io/4.1/api/io/netty/handler/ssl/SslHandler.html), and [Bouncy Castle Java 1.86](https://www.bouncycastle.org/download/bouncy-castle-java/). These are candidates, not dependencies added by this design.

The repository still pins `netty-incubator-codec-native-quic 0.0.73.Final`.
The [Netty QUIC codec repository](https://github.com/netty/netty-incubator-codec-quic)
was archived by its maintainers in May 2026 and says QUIC support moved to
Netty 4.2. Before adding another TLS layer, review support and Windows/JDK
compatibility for the pinned transport versus a migration. This is an open
dependency decision; this design does not silently change the transport.
The [Netty 4.2 BOM](https://github.com/netty/netty/blob/4.2/bom/pom.xml)
lists a Windows x86-64 native QUIC artifact, while the
[4.2 API](https://netty.io/4.2/api/io/netty/handler/codec/quic/QuicStreamChannel.html)
uses a different QUIC package. Artifact availability alone does not establish
compatibility with this project's Java runtime, shaded JAR, EOF behavior, or
performance gates.

**Explicit non-goals:** public relay hosting; account service; permanent host identity; guest identity beyond BTA online mode/whitelist; zero-downtime TCP migration; hiding metadata from the relay; Linux/ARM64 support; changing default limits; weakening existing TLS, archive, path, recovery, or process controls.
